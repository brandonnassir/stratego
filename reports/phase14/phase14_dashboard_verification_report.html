01The one decision worth reviewing

The dashboard imports nothing from stratego, and therefore no torch.

Every phase14_* module reaches torch through the contract chain — phase14_contract → phase9_contract → warmstart_contract → stratego.model → torch — measured at 205 MB resident and 0.46 s to import. Reusing scripts/phase14_status.py would have put a GPU-capable runtime inside a process whose job is to read seven JSON files.

Worse, its build_status() calls resume_checkpoint_state(), which calls HotCheckpointRing.load_latest() → torch.load() of a full model and optimizer state, then recomputes an integrity digest over it — per status read. That is correct for a resume decision and unusable at a ten-second refresh.

So the dashboard is pure stdlib. The task forbids importing the model; making it structurally impossible is stronger than promising not to.

The cost of that choice, and how it is contained. The frozen constants are mirrored in contract.py, and duplicating a frozen number is how a dashboard ends up confidently displaying last month's deadline. TestMirroredContract therefore imports the real frozen modules — in a test process, where torch is free — and asserts all 26 mirrored values equal their source, that the segment and learning-rate functions agree with phase14_clock at the 132-hour boundary, and that RunPaths resolves to the same paths as Phase14Storage. If the contract moves, the test fails rather than the dashboard lying.

3a · One gap found, and closed without touching frozen code

The accepted supervisor's launch record carries learner_pid but not its own PID, so a naive reading leaves "is the supervisor alive?" permanently unknown — one of the questions §10 specifically asks the dashboard to answer.

Changing the supervisor to log its PID would move sealed Phase 14 code. It does not need to: spawn() gives the learner a new session, not a new parent, so while the supervisor lives it is the learner's PPID.

The derivation also answers something a logged PID could not. A learner whose parent is PID 1 has been reparented to launchd — the supervisor died and left it running. Training continues, but nothing is watching for the next crash, and without this an operator would have to notice by hand.

04Zero model, zero MPS

  • A subprocess that imports the dashboard and builds a full status document reports its loaded torch / stratego / numpy modules as [].
  • No checkpoint file is ever opened. The hot panel reports validated: false with the note "validity is the supervisor's call", and a test asserts the checkpoint's mtime is unchanged after a status read.
  • lsof on the live server process: 0 torch or Metal files open.
  • vmmap shows Metal/MPS framework mappings — and a bare python -c "time.sleep(25)" shows exactly the same 69 mappings and 16 IOAccelerator regions. Those are the macOS dyld shared cache present in every process; the dashboard adds nothing and initialises no Metal device.

05Read-only, three ways

  • Empirical. Every file under the run root and hot ring is digested (size, mtime_ns, SHA-256), the dashboard is refreshed 100 times with all caches expired, and the tree is digested again. Identical, with no file created or removed.
  • Structural. The package source is parsed with ast; no call to write, mkdir, unlink, rmtree, rename, chmod, utime, fsync or copy exists anywhere, and the only open() in the package is mode "rb".
  • Reading a run directory that does not exist does not create it — a monitor that brought the production run directory into existence by looking at it would be a real defect. It reports NOT STARTED.
  • HTTP. POST/PUT/PATCH/DELETE return 405 pointing at the runbook; any path outside the five-route allowlist returns 404. Binding anything but loopback is refused unless explicitly overridden.
  • UI. The page contains no <input>, <button>, <form>, <select>, <textarea> or contenteditable, and exactly one fetch(), which is a GET. There is no control for LR, opponent mixture, setup selector, batch size, loss weights, pool strategy, search mode, duration, deadline, optimizer settings, checkpoint deletion, a new run, or a restarted clock — absent, not disabled.

06Training independence

Against a stand-in trainer that appends telemetry continuously, all six checks from §15:

  • the trainer runs with the dashboard absent;
  • the dashboard attaches to an already-running trainer and picks up its rows;
  • the dashboard is SIGKILLed mid-run and the trainer keeps advancing — repeated against the live run in §3b, where a supervisor, a learner and six real pool workers all survived the dashboard's death;
  • closing the browser changes nothing: the page stops polling when hidden, and the server does no work between requests;
  • a restarted dashboard reconnects and reports the same authoritative total, with the tree digest unchanged;
  • lsof confirms it holds no descriptor on any run file between requests — nothing for the trainer, supervisor, checkpoint writer or rollout store to contend with.

A missing run directory, a torn manifest.json, a truncated state.json, an unparseable telemetry log and a half-written supervisor line are each handled as reported absences rather than exceptions — the moment an operator most needs the page is the moment the run is in the worst shape.

09Known display limitations

  • Training numbers are up to one iteration (~21 min) old. The learner publishes one telemetry row per completed iteration; that is the design, not a fault. It is stated on the page, and telemetry is graded watch past 45 minutes. The fast-moving fields — wall clock, learner and loader liveness, checkpoint ages, disk, supervisor events, in-flight game count — are all live and independent of that cadence.
  • Checkpoint validity is not checked, only presence, size and age. Validating means torch.load; the supervisor is the authority and the panel says so.
  • Before the first checkpoint and telemetry row, most training fields read — and health reads unknown. That is the honest state of a run in its first iteration.
  • Games/hour is a run-average — committed games over elapsed wall-clock — so it dilutes across downtime rather than reporting an instantaneous rate. The instantaneous rate is the separate games/s from the latest row.
  • The first read after the external volume has been idle can take a few seconds while the drive wakes — measured 2.96 s once, then 1.3 ms. Not a recurring cost.
  • One run at a time; --external-root selects which.
  • Verified in Chromium at 1280 px in both colour schemes. The layout is responsive but has not been exercised on a phone.
